Module 1

Le Modèle Séquentiel

Parfaitement Adapté à l'Industrie

Production d'une Voiture

Conception → Assemblage → Peinture → Contrôle → Livraison
  • Processus linéaire et séquentiel
  • Chaque étape doit être parfaite
  • Pas de retour en arrière possible

Exemple : Rappel de Véhicules

Cas réel : Airbag défectueux

  • Découvert après 2 ans de production
  • 2,6 millions de véhicules rappelés
  • Coût : 900 millions d'euros
  • Image de marque détériorée

Pourquoi ça Marche ?

🚗 → ❌ Modification

  • Contrainte physique : produit non modifiable
  • Rappel de véhicules = extrêmement coûteux
  • Mieux vaut tout vérifier avant
  • Conception minutieuse justifiée

Module 2

L'Adaptation au Logiciel

Le Waterfall et le Cycle en V

Le Modèle Waterfall

Analyse & Conception (3 mois)
        ↓
   Développement (6 mois)
        ↓
      Tests (2 mois)
        ↓
   Déploiement (1 mois)

Total : 12 mois

Inspiration directe de l'industrie

Exemple Concret : Projet E-commerce

Cycle de 12 mois

  • Jan-Mars : Spec complète du site
  • Avril-Sept : Développement isolé
  • Oct-Nov : Tests et découverte des bugs
  • Décembre : Mise en production
  • 🎄 Problème : les specs ont 1 an !

L'Avantage du Logiciel

💻 → ✅ Modification

  • Application modifiable après production
  • Coût relativement faible
  • Déploiement d'une nouvelle version
  • Mais on a gardé le modèle séquentiel !

Les 3 Problèmes du Waterfall

  1. Passages de relais : silos, malentendus, délais
  2. Effet tunnel : 6 mois sans retour
  3. Dette technique : peur de refactorer

"Ça marchait chez nous"

Problème 1 : Les Passages de Relais

Dev : "C'est fini !"
  ↓
QA : "Euh... c'est quoi ce bouton ?"
  ↓
Dev : "Ah oui, j'ai oublié de documenter"
  ↓
QA : "Et ça fait quoi en cas d'erreur ?"
  ↓
Dev : "Bonne question... 🤔"

Perte de contexte à chaque transfert

Problème 2 : L'Effet Tunnel

Exemple : Application mobile

  • Développement de 6 mois
  • Livraison : septembre 2023
  • Découverte : iOS 17 a changé l'UI
  • Le design spécifié en mars est obsolète
  • Refonte nécessaire avant la sortie

Problème 3 : Dette Technique

Mois 1-2 : Code propre, bien structuré
    ↓
Mois 3-4 : "On verra le refactoring plus tard"
    ↓
Mois 5-6 : "Surtout ne rien toucher !"
    ↓
Intégration : Fichiers de 3000 lignes
              Fonctions imbriquées sur 8 niveaux
              Tests ? Quels tests ?

Le Coût Réel

  • 📊 Productivité : -40% en fin de projet
  • ⏰ Délais : +3 mois en moyenne
  • 💰 Budget : dépassement de 50-200%
  • 😓 Équipe : burnout et turnover
  • 📉 Qualité : bugs en production × 5

Module 3

La Crise de l'Intégration

Quand la Vitesse devient un Piège

Développer Plus Vite ?

Vitesse ↑ + Intégration Rare = 💥

  • Les problèmes sont exacerbés
  • Pas éliminés !

Exemple : L'Intégration de l'Enfer

Projet réel : 5 devs, 2 semaines de code

  • Lundi : "On intègre vendredi"
  • Vendredi : 847 conflits Git
  • La fonction getUserData() a 3 versions différentes
  • Résolution : 3 jours (au lieu de 1h prévue)

L'Enfer de l'Intégration

  • 🔴 Effondrement de la productivité
  • ⏰ Délais imprévisibles
  • 🐛 Conflits sémantiques
  • ❌ Refactoring impossible
  • 📈 Bugs cumulatifs

Conflits Sémantiques : Exemple

Dev A (branche feature-A):
  function calculatePrice(item) {
    return item.price * 1.20; // TVA 20%
  }

Dev B (branche feature-B):
  function calculatePrice(item) {
    return item.price * 0.80; // Réduction 20%
  }

Merge : ✅ Pas de conflit Git !
Runtime : 💥 Prix incohérents

Le Cercle Vicieux

Plus on attend
    ↓
Plus c'est difficile à intégrer
    ↓
Plus on hésite à intégrer
    ↓
Plus on attend...

Chiffres Réels

Étude de cas : Entreprise 200 devs

  • Intégration mensuelle → 5 jours de merge
  • Intégration hebdo → 1 jour de merge
  • Intégration quotidienne → 1h de merge
  • Temps gagné : 80% !

Module 4

La Solution

L'Intégration Continue et l'Agilité

Deux Pratiques Indissociables

Agilité

  • Petites étapes
  • Sprints courts
  • Produit viable

CI

  • Intégrations fréquentes
  • Tests automatisés
  • Feedback rapide

L'une ne peut exister sans l'autre

Exemple : Avant/Après

Avant (Waterfall) Après (Agile + CI)
Release tous les 6 mois Release toutes les 2 semaines
Intégration : 1 fois Intégration : 50+ fois
Feedback : après 6 mois Feedback : chaque sprint
Bugs trouvés : 200+ Bugs trouvés : 20-30

4 Pratiques Clés de la CI

  1. Intégration fréquente : quotidienne (ou plus)
  2. Automatisation du build : zéro erreur humaine
  3. Code auto-testé : tests = confiance
  4. Correction immédiate : 🔴 → priorité #1

Pratique 1 : Intégration Fréquente

Règle : Fusionner au moins 1x/jour

  • Matin : récupérer la mainline
  • Développer sur une feature courte (2-4h)
  • Après-midi : commit + push
  • Pas de branches qui vivent > 1 jour

Pratique 2 : Build Automatisé

git push
  ↓
Trigger automatique du pipeline
  ↓
npm install
npm run lint
npm run build
  ↓
✅ Build réussi en 3 minutes

Pratique 3 : Code Auto-Testé

Couverture de tests :

  • Tests unitaires : fonctions critiques
  • Tests d'intégration : API endpoints
  • Tests E2E : parcours utilisateur
  • Objectif : 80%+ de couverture
  • Temps d'exécution : < 10 minutes

Exemple de Test Automatisé


// tests/user.test.js
describe('User Registration', () => {
  it('should create user with valid email', async () => {
    const user = await createUser({
      email: 'test@example.com',
      password: 'secure123'
    });
    expect(user.id).toBeDefined();
    expect(user.email).toBe('test@example.com');
  });

  it('should reject invalid email', async () => {
    await expect(createUser({
      email: 'invalid-email',
      password: 'secure123'
    })).rejects.toThrow('Invalid email');
  });
});

Pratique 4 : Correction Immédiate

La règle d'or :

  • Build 🔴 = Tout le monde s'arrête
  • Option 1 : Fix en < 10 minutes
  • Option 2 : Revert du commit
  • Pas de nouveau commit tant que 🔴
  • Mainline toujours verte = confiance

                                       ↓

Les Bénéfices

  • ✅ Réduction des risques
  • 🔄 Refactoring sans crainte
  • 📝 CI as Code (GitLab CI/CD)

CI as Code avec GitLab


# .gitlab-ci.yml
stages:
  - build
  - test
  - deploy

build:
  stage: build
  script:
    - npm install
    - npm run build
  artifacts:
    paths:
      - dist/

test:
  stage: test
  script:
    - npm run test:unit
    - npm run test:integration
  coverage: '/Lines\s*:\s*(\d+\.\d+)%/'

deploy:
  stage: deploy
  script:
    - kubectl apply -f k8s/
  only:
    - main

Module 5

De la CI au CD

Le Déploiement Continu

CD = CI + Déploiement Auto

Commit → Build → Tests → Deploy
         ✅      ✅       🚀

Pourquoi s'arrêter à l'intégration ?

Exemple : Avant CD

Processus manuel de déploiement :

  1. SSH sur chaque serveur (5 serveurs)
  2. git pull sur chacun
  3. Redémarrer les services
  4. Vérifier les logs
  5. Temps total : 2-3 heures

Et si erreur → rollback manuel 😰

Deux Révolutions Technologiques

  1. Kubernetes : Orchestration de conteneurs
  2. Infrastructure as Code : Terraform, Ansible

Avant : déploiement complexe, manuel, fragile
Après : kubectl apply

Exemple : Déploiement Kubernetes


# deployment.yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: mon-app
spec:
  replicas: 3
  template:
    spec:
      containers:
      - name: app
        image: registry.com/mon-app:v1.2.3
        ports:
        - containerPort: 8080
        resources:
          requests:
            memory: "256Mi"
            cpu: "250m"

kubectl apply -f deployment.yaml → Déployé !

Le Pipeline de Déploiement

1. Commit Build (tests unitaires < 10 min)
           ↓
2. Tests avancés (fonctionnels, perf, sécu)
           ↓
3. Build Docker image
           ↓
4. Push to registry
           ↓
5. Deploy to staging
           ↓
6. Tests de fumée
           ↓
7. Deploy to production

GitLab CI/CD : Pipeline Complet


build-docker:
  stage: build
  script:
    - docker build -t $IMAGE:$CI_COMMIT_SHA .
    - docker push $IMAGE:$CI_COMMIT_SHA

deploy-staging:
  stage: deploy-staging
  script:
    - kubectl set image deployment/app app=$IMAGE:$CI_COMMIT_SHA
    - kubectl rollout status deployment/app
  environment:
    name: staging
    url: https://staging.example.com

deploy-production:
  stage: deploy-production
  script:
    - kubectl set image deployment/app app=$IMAGE:$CI_COMMIT_SHA
    - kubectl rollout status deployment/app
  environment:
    name: production
    url: https://example.com
  when: manual  # Déploiement manuel en prod
  only:
    - main

Zero downtime ! ✅

Le Problème "Ça Marche sur ma Machine"

Avant:
Dev 💻 → QA 🖥️ → Prod 🖥️
  ✅       ❌      ??

(Python 3.9) (Python 3.8) (Python 3.7)

Avec Docker:
Dev 📦 → QA 📦 → Prod 📦
  ✅       ✅       ✅

(Même image Docker partout)

Exemple : Dockerfile


FROM node:18-alpine

WORKDIR /app

# Installation des dépendances
COPY package*.json ./
RUN npm ci --only=production

# Copie du code
COPY . .

# Build de l'application
RUN npm run build

# Exposition du port
EXPOSE 8080

# Commande de démarrage
CMD ["npm", "start"]

Exemple Complet : Du Code à la Prod

  1. Dev fait un git push
  2. GitLab CI démarre automatiquement
  3. Build + Tests (5 min)
  4. Construction de l'image Docker
  5. Push vers le registry
  6. Déploiement sur staging
  7. Tests automatisés sur staging
  8. ✅ Validation manuelle
  9. Déploiement en production
  10. Monitoring automatique

Temps total : ~15 minutes

Monitoring & Rollback

Deploy v2.0 → Monitoring détecte :
              - Error rate: 5% → 15%
              - Response time: 200ms → 2s
                ↓
              Alerte automatique
                ↓
kubectl rollout undo deployment/app
                ↓
              Retour à v1.9 en 30 secondes
